# Linux 等待保存时清空列表验收

日期：2026-09-14。承接[活动转换清空验收](LINUX_CLEAR_ACTIVE_ACCEPTANCE.md)，补齐等待保存结果时清空的固定 deb GUI 回归。生产队列和安装包不变。

## 实现与 review

复用保存恢复场景的隔离 PNG 和 1000 个同名碰撞文件，实际转换为 WebP 并因命名冲突进入 `awaiting_save`。确认 attempt=1、无已发布结果，且私有缓存中存在一份 WebP 载荷。通过可见 `Clear file list` 按钮聚焦并发送 Return，要求：

- 队列清空，processing、clearing、closing 均为 false；epoch 更新，输出目录及本会话授权保留。
- 已观测缓存路径消失，缓存扫描不再找到 WebP 载荷；同一应用进程仍存活。
- 原图、1000 个碰撞文件、已有保存结果的内容不变，结果目录不产生额外文件。

再次从真实文件选择器导入原图，要求新任务 ID、attempt=0，改选正常输出目录并用键盘转换。新任务在清空后的 epoch 以 attempt=1 保存，检查 WebP 头、WebKit 解码尺寸及文件集合；再清空列表后新结果仍在。外层安装验收在卸载后继续核对保存结果摘要。

Review 重点与修正：

1. 不把列表为空当作缓存已释放；等待具体载荷路径消失并扫描隔离缓存。仅 ENOENT 代表消失，其他文件系统错误继续失败。
2. 复用既有选择器、缓存扫描与 PID/start-time 身份检查，避免新增测试专用生产接口；输入和碰撞文件均为测试资产。
3. 前后按文件集合与字节比较，区分删除暂存结果和误删用户文件。缓存范围是本场景的 WebP 载荷，不声称清理了全部元数据或所有格式缓存。
4. 新导入不复用旧任务 ID，实际解码保存结果；未通过源文件移除来证明是否发生新编码，因此不将此写为编码进程追踪证据。
5. 门禁增加两项，要求完整二十六项；旧二十四项、缺项、重复项、错误状态、架构或应用哈希均拒绝。历史报告保持原计数，不回填为二十六项。

本轮交付为验收覆盖，本机和双架构回归均未发现需要修改生产逻辑的缺陷。

## 边界

本新增场景是单项 WebP 的文件名碰撞保存失败，不注入磁盘耗尽，不修改应用缓存。它不替代多项未保存结果、单项移除、升级、Snap strict、Windows/macOS GUI 或商店验收。沿用的其他活动转换场景仍含 SIGSTOP 注入；R6 不能据此整体标为完成。
