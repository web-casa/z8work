## 1. 起点与最终交付

截至 [Phase 23](PHASE23_IMPLEMENTATION.md)，Linux ARM64 开发环境已验证原生图片、PDF、音频和有限文档转换，以及队列、取消、恢复、批量设置、预览、存储预检、私有工作目录和脱敏诊断。普通单文件保存失败仍需重新编码；引擎仍在 Tauri setup 中同步加载。既有 Windows/Snap 候选早于最新功能，不能作为当前版本的安装证据。

制定方案时依据工作区源码与 Phase 23 源码收据，而非仅 Git HEAD；当时桌面目录及许多脚本尚未提交。R1 已整理为本地提交并验证隔离 checkout，详见 [Phase 24](PHASE24_IMPLEMENTATION.md)。历史测试数只表示当时覆盖，不与新阶段混用。

七个阶段的终点是：**功能范围冻结、缺口修复、目标平台原生安装验收通过、许可材料齐备、可提交的 V1 候选及发行交接记录**。上传、审核与公开分发另记外部状态；不能承诺商店在七个开发阶段内批准。缺少机器、账号、身份或证据时保留未完成状态，不以文档代替验收。

| ------------------ | ------------------------------------------------------------------------------------------------------------ |

这是为了完成首版而对原方案“当前支持的文档转换、多语言”等宽泛措辞作出的明确收敛。网页已有更多格式和语言保持原状。其他图片/PDF 输出、更多文档格式和语言列入 V1.1，不在实现中随意增加或悄悄开放；如需改首版范围，先更新本表及验收矩阵。

## 3. R1 / Phase 24：范围、基线与平台准备

工作：

1. 以当前源码核对上述输入→输出路线、语言、预算、发行渠道，补齐到可追踪矩阵。每项关联实现位置、样本、目标平台和验收阶段；旧文档标明历史状态。
2. 整理现有未提交桌面代码及文档，区分源码、可公开样本、构建产物和本机证据。形成可重建的提交基线与锁文件；不覆盖用户改动，不把私有文件、凭据或大体积临时产物加入仓库。
3. 清点原生 Windows x64、Linux AMD64 strict 桌面、macOS ARM64 的可用环境。记录实际访问/预检结果、SDK/运行依赖、测试账户和平台执行人或执行入口；未知项写未执行。
4. 提前检查 Store 身份、Snap 注册名、测试证书等来源。[当前提交配置](../../packaging/desktop/store/submission.json)中 Identity/Publisher 等仍为空，不从产品名推导。缺失时形成具体待提供项，继续不依赖它们的开发。
5. 审查已有 [desktop CI](../../.github/workflows/desktop.yml)，补必要的共享代码路径触发、前端/原生测试、构建和证据留存；现有 CI 已有测试，不重做一套平行脚本。固定发行所用工具链，更新验证另行运行，避免浮动工具链破坏重建依据。远端未运行时不得写 CI 通过。
6. 先筛查三端引擎来源、构建可得性、许可和完整源码材料风险，尽早验证各目标最小包的准备路线；R5 再完成候选级闭合。记录启动、转换、取消、峰值内存/磁盘的测试场景和计量方法，R4 冻结性能阈值，不能拖到 R6 才定义。

验收：基线可在隔离目录按锁文件准备；矩阵和命令指向实际源码；每个平台都有通过/失败/未执行及缺项说明。R1 的清点可完成，但目标环境未就绪会继续阻塞对应 R5/R6 门槛，不能被“清点完成”关闭。

交付：Phase 24 实施记录、机器可读或表格能力矩阵、基线标识、环境/账号缺项及后续验证入口。

## 4. R2 / Phase 25：仅重试保存与结果暂存

状态：已完成，见[实现、review 和本机验收](PHASE25_IMPLEMENTATION.md)。以下保留本阶段原定要求；已冻结会话空闲 30 分钟、合计 1 GiB、单文件 256 MiB 的暂存限制。

工作：

1. 在现有 Rust 队列与 `ConversionResult` 周围分开“编码结果已验证”“等待保存”“已保存”。优先扩展已有契约、快照和执行轮次，不让 UI 成为结果状态来源。
2. 编码成功而发布失败时，保留受控私有目录中的有效结果；用户可重新选择授权输出目录并只重试保存。重试幂等、禁止覆盖、跨盘发布、保存结果校验保持现有约束。
3. 暂存绑定任务、执行轮次、转换参数与已验证结果身份；UI 只传结果/任务标识。更改格式或参数不得误用旧结果。保存完整暂存结果不要求重新读取源文件，也不因此授予源路径或任意目录权限。
4. 建议起始策略：仅本次进程会话保留，空闲有效期 30 分钟，全部待保存结果合计上限 1 GiB，同时满足磁盘安全余量；R2 压测后冻结常量。超过预算、过期或暂存受损时明确说明需重新转换，不无限保留。计时使用单调时钟，保存中的结果不可被过期清理；预算占用必须计入并发保存和转换。
5. 单独定义取消编码、取消输出选择、移除/清空、退出、崩溃和历史恢复。取消选择允许返回待保存；移除等待保存操作结束后释放；退出提示包含待保存结果。重启只恢复可解释的任务状态，不自动信任旧临时文件或自动重跑。
6. 扩展 Phase 21 工作目录所有权/清理和 Phase 22 容量预检；不清扫用户输出目录。PDF 既有成功页与重试机制保持独立，不把整份 PDF 的缓存强塞入单文件暂存逻辑。

验收：通过引擎调用计数证明保存重试未再编码；验证选择取消、权限撤销、目录切换、同名竞争、跨盘、超限/过期、缓存篡改、移除/退出竞态及历史 schema 迁移。已有结果和原文件字节不变，前端不能提交任意保存路径；本机真实 GUI 走通失败后重试。

交付：后端状态/暂存管理、前端操作与双语提示、契约和故障测试、Phase 25 实施及 review 记录。

## 5. R3 / Phase 26：启动、导入、进度与错误

状态：已完成，见[实现、review 和本机验收](PHASE26_IMPLEMENTATION.md)。以下保留原定要求；共享包完整性失败仍整体拒绝，底层阻塞 IO 和目标系统故障仍需后续验收。

工作：

1. 窗口先显示，引擎在后台按项准备；缺失/失败只限制对应格式。禁止 UI 主线程承担引擎探测、队列大快照或文件系统长操作；探测有界限、取消和退出路径。
2. 早期原生选择/拖放通过已有授权登记有界排队，UI 就绪后从快照获取。引擎未就绪不能误报“不支持”；单实例与退出期间导入不重复执行。系统文件关联仍留后续。
3. 对已有 FFmpeg 路线加入有界、节流的机器进度解析；时长未知时展示阶段。PDF 延续页进度，其他引擎不伪造百分比；只有实际保存完成才显示完成。
4. 为启动、导入、转换、暂存和发布定义稳定错误分类及受控参数，逐步替换字符串推断，补 TS/Rust 契约测试。原始引擎日志不直接成为可导出诊断或带 HTML 的 UI 内容。

验收：注入阻塞的引擎探测，证明探测释放前首屏已可交互，取消/退出可以响应；慢/坏/缺失引擎不阻止其他已就绪类别。早期导入队列沿用现有导入/任务数量上限并测试溢出提示，不丢失、不重复、不越权；重连快照与进度事件有序，旧轮次事件失效；未知时长、异常进度、长日志、取消/退出不误标成功。R2 保存中状态、旧历史和诊断 schema 的兼容测试通过。

交付：启动状态与异步生命周期、进度/错误契约、真实 GUI 和后端测试、Phase 26 记录。

## 6. R4 / Phase 27：产品体验、隐私及格式质量

状态：产品体验与基础格式开发已完成，见[实现及 review](PHASE27_IMPLEMENTATION.md)、[84 条格式矩阵](PHASE27_FORMAT_MATRIX.md)及[性能预算与缺项](PHASE27_PERFORMANCE.md)。本机参考不能替代三端验收；首次配置、大型 PDF/音频、导入/取消延迟及目标候选资源测量仍未执行，必须补齐才能关闭对应性能验收。PDF ICC 构建能力也未关闭，R5 核对候选构建选项、R6 使用含 ICC 的 PDF 实测。以下保留原定要求。

工作：

1. 中英文覆盖全部首版界面与新增错误；右上角语言切换可见，沿用像素图标。走查键盘导航、焦点、禁用/加载状态、屏幕阅读标签、最小窗口和高缩放；清空任务明确说明不会删除原文件或磁盘结果。
2. 展示“在此设备处理”“文件上传 0 B”，解释这是本地转换能力声明，不是全机或应用全部网络流量的实时仪表。只在已核实的本地执行路线显示，未知路线不能继续声称 0 B；外链交给系统浏览器，更新活动另行解释。
3. 复用 [环保计算模块](../../src/lib/util/environmental-impact.ts)的纯计算意图，按原生队列数据适配，不复用浏览器 `File` 或网页 store。只统计已保存的图片结果，按任务去重，大结果抵消小结果；清空后不保留虚构累计贡献。源文件仍保留时说明是“结果相对原图的潜在存储减少”，不声称实际释放磁盘或已抵消碳排放。
4. 环保说明可离线阅读，列估算假设、时长、模型版本、来源与局限；实施时复核引用。PDF、音频和文档不套用图片压缩统计，失败、暂存和部分结果不提前计入。
5. 对冻结路线建立真实可解码样本：透明度、方向、ICC、8/16 位、HEIC、AVIF/WebP 质量和体积、PDF 字体/页数/命名、音频时长/声道、文档纯文本。AVIF 不承诺总比 WebP 小；禁止为追求体积悄悄换输出格式或破坏质量预设。
6. 复核预览、队列、保存、设置和诊断的用户路径，冻结首版功能；新增格式或语言转入明确的后续列表。以 R1 固定场景形成各目标性能预算表，注明硬件、样本和次数；尚未取得目标机器的预算标为未执行并阻塞对应性能验收，不把 Linux ARM64 数值当成三端基准。

验收：真实 UI 截图与语言/键盘验证；统计正确处理重试、变大、清空、未落盘和重复事件；首版每条路由有样本和语义断言，不能只检查扩展名/非空文件。本阶段开发环境通过不替代 R6 最终安装包复测。

交付：产品 UI 与文案、离线隐私/环保说明、冻结格式/样本矩阵、Phase 27 记录。

## 7. R5 / Phase 28：自包含构建、依赖与许可

当前状态：开发与 review 进展见 [Phase 28 实施记录](PHASE28_IMPLEMENTATION.md)及[候选交接](PHASE28_CANDIDATES.md)。Linux ARM64 本地包、当前 Windows 开发 MSIX 和 AMD64 Snap 已重建；macOS 实际候选、完整许可/源码与部分升级输入仍未完成，不将 R5 标为通过。

工作：

1. 复用既有 Linux/Snap、Windows/MSIX 脚本，补 macOS ARM64 构建与引擎布局。锁定 app、原生引擎及 delegates、字体/数据资源和构建工具来源；隔离环境不依赖开发机 PATH 中的引擎。
2. 统一 app 版本、各渠道包版本与身份的映射，查询实际商店配置及执行时官方规则；开发身份与正式身份分开，不虚构版本或发布者。构建记录包含源码提交、锁文件、feature、资源清单和工具链。
3. 对最终载荷检查架构、动态依赖、引擎策略、Pandoc 数据与 MuPDF 字体等资源。发行包关闭开发引擎覆盖、测试 IPC/driver 服务与网页 WASM/SW 入口；正式 GUI 验收优先 OS 自动化，不把测试构建证据替代正式包。
4. 按实际二进制收敛依赖、许可证、源码、补丁、配置和重建说明，并提供应用内离线许可入口。历史 170 组源码校验不等于当前三端完整许可验收；组件组合存在未解决分发问题时，该候选不进入发布。
5. 更新 CI 的构建/产物检查与失败阻断。为 R6 准备同身份、较低版本的受控升级测试包；标为合成迁移样本，不能声称它是已公开旧版。

验收：目标架构自包含候选可按记录重建；记录每次哈希，不预设构建必然逐字节确定。包内缺文件/错架构/配置漂移会失败；核心实际转换先做包内 smoke。缺正式身份可做开发候选，但正式候选门槛继续未完成。

交付：更新后的三端候选与构建脚本、依赖/许可清单、升级输入、Phase 28 记录。所有候选包含 R2–R4 最终功能，旧 MSIX/Snap 仅保留历史用途。

## 8. R6 / Phase 29：原生安装、故障与升级验收

本轮进展见 [Phase 29 实施与 review](PHASE29_IMPLEMENTATION.md)：真实只读挂载、inode/磁盘耗尽及权限撤销恢复已在 Linux ARM64 隔离环境验证，并修复 inode 耗尽的错误分类。macOS 平台/最低系统版本门禁已补齐。以下三端安装、升级和剩余故障项目仍按原验收要求执行。

工作：

1. Windows x64：只在测试副本上进行必要的侧载签名，保留正式原件；实际安装位置启动，验证菜单激活、WebView2 准备/缺失提示、离线转换、对话框、中文路径、进程树退出、升级与卸载，执行适用的 WACK。解析或交叉编译不算原生通过。
2. Linux AMD64：真实 strict Snap 环境安装最终包，核对载荷，验证 portal 选择与取消、输入/输出分别授权、home/隐藏路径/外接盘、断网转换、refresh 与数据兼容。不能以 devmode 或 ARM64 开发 GUI 替代。
3. macOS ARM64：本地验证用 app 在目标系统和干净账户运行，验证原生引擎/dylib、文件选择与拒绝、输出、重启设置/历史、取消退出和版本替换。保留本地测试信任限制，不宣称已完成公开分发。
4. 三端运行 R4 样本矩阵与关键 GUI 路径；检查进程退出码、实际输出和权限。R2 保存恢复、R3 启动/事件、R4 统计和诊断脱敏均进入安装包回归。
5. 在隔离环境做真实受限磁盘/配额、只读目录、断盘、异常终止、睡眠恢复、更新中断、队列上限与大文件压力验证；记录耗时、峰值内存/磁盘和清理结果。危险故障只用可恢复测试盘/账户，不填满共享服务器磁盘。
6. 修复故障后重建受影响候选并重跑相应安装/业务路径；任何平台共享源码变化都检查其他目标影响，不把旧哈希报告重新贴到新包。

验收：各必需平台项目结果为通过，或有与首版范围一致且写明理由的不适用。失败和未执行均不能关闭验收；平台缺失时继续其他工作，但 R6 不标完成。性能阈值在 R1 记录测试配置、R4 基线后冻结，R6 不为通过测试临时放宽。

交付：确切候选的三端安装与转换报告、截图、压力/故障报告、已修复问题及残余限制，Phase 29 记录。

## 10. 共用完成标准与进度规则

- 阶段状态使用未开始、进行中、待外部条件、完成；验收结果只用通过、失败、未执行、不适用，并写原因。当前 R1–R4 开发已完成，[R5 / Phase 28](PHASE28_IMPLEMENTATION.md)已完成本机候选重建与工具开发，macOS 实际候选、许可/源码闭合及部分升级输入仍待完成；R6 已完成本机故障验证、仍待三端安装及剩余验收；R7 已开展独立门禁 review 与交接准备、仍未完成；R4 尚未执行的性能/目标包检查继续阻塞对应验收；R1 完成条件清点不关闭 R5/R6 的外部条件缺项。
- 每阶段记录范围、实际改动、review 问题与修正、执行命令、真实结果、剩余限制和下一阶段入口。保留失败证据，不用最终通过覆盖之前问题。
- 前端/契约变动运行桌面类型检查、相关 Node 测试和构建；Rust 变动运行相关原生/app 测试、fmt 与 Clippy；影响跨端执行则加原生目标验证。共享网页代码变动补网页相应回归，纯文档仅做格式/链接/一致性检查。
- 使用已有 `desktop:check`、`desktop:test:ui`、`desktop:build` 及平台脚本；新命令先实现并验证再写进执行说明。单元 mock、交叉编译、包 smoke、真实 GUI、安装验收分层报告。
- 候选证据记录渠道、OS/架构、源码提交及工作区收据、工具链、包哈希、应用/引擎版本、feature、执行环境、测试结果与报告路径。公开证据使用可分发合成样本，不泄露用户路径或文件。
- 阶段可以分批交付，完成标记必须满足该阶段条件。无法取得外部条件时交付可运行的验收入口并保留阻塞，不能无限添加本地工具后宣称 V1 完成。
