## 产品边界与长期决策

- 桌面端采用 Tauri 2 + Rust，调用随包的 ImageMagick、FFmpeg、Pandoc 和 MuPDF 等原生引擎；用户文件仍在本地处理。
- “网页端能转换”与“某个原生引擎列出 coder”都不能自动说明桌面包可公开支持；最终包必须有逐路实测证据。
- 当前不开发视频格式；不把视频编码、OCR、完整办公文档互转、MAS 或 ARM64 Snap 混入本轮格式扩展。
- 发行、安装、签名、公证、商店审核、升级和性能验收是独立门禁。构建成功不等同于可以发布。

## 接下来安排

按以下顺序推进，并在每一步完成后把命令、对象、哈希、环境、结果和未覆盖范围写入证据目录与本页链接的专题记录。

1. **完成当前 ARM64 retry-8。** 静态真实文档夹具已通过独立 reader 验证；下一次完整重跑必须保留开始/结束时间、verifier SHA-256、精确停止路由和非空报告。
2. **修复最小根因并重新 review。** 只改已证实路径；新增回归后重跑 Rust、前端和安全/差异检查。保持本地、离线、白名单与输出读回约束。
3. **闭合 Linux ARM64 候选。** 在最终提取归档上通过完整格式矩阵、质量门禁、DEB 内容一致性、安装/卸载和真实 GUI/保存/取消验收，归档非空报告与哈希。
4. **逐平台复制验收，而非复制结论。** 依次为 Linux AMD64、Windows AMD64/ARM64、macOS AMD64/ARM64 构建或验证实际目标包；记录架构、动态依赖、签名、安装方式和限制。
5. **回到正式桌面发行门禁。** 按[剩余清单](REMAINING_STATUS.md)处理 Windows MSIX、Snap strict、版本升级、性能/故障、许可源码、稳定下载和商店材料。格式扩展全部通过也不能跳过这些门禁。
6. **最终发布 review。** 仅在每个目标包的实际验收、来源/许可证和公开资料同步完成后，更新下载页与格式报告，并按届时授权提交 GitHub Release、Microsoft Store 或 Snapcraft。

## 记录规则

- 新的候选、复现或修复必须建立独立证据目录，保留原始日志或其有界摘要、SHA-256 和执行命令；失败记录不能被成功记录覆盖。
- 文档中必须区分“源码测试通过”“最终包验收通过”“实际安装使用通过”和“公开发布通过”。
- 对外格式说明只从已通过的目标包结果生成；不得从开发机 PATH、CI 成功状态、旧包或官方格式清单推导。
- 遇到超时、依赖差异或平台特有问题，先记录可复现条件与证据，再修改实现或扩展时限。
