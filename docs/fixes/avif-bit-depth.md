# AVIF 输出位深与体积修复

用户反馈同一张 PNG 转 WebP 是 329.4 KB，转 AVIF 是 1.5 MB。使用用户提供的本地文件、项目实际 WASM 及质量 100，精确复现这两个数值。

## 原因与修复

输入为 1170 × 2532 的 16 位 PNG（1,673,838 字节）。当前 `magick-wasm@0.0.43` 的 `Quantum.depth` 为 8，解码后的像素只有 8 位精度，但 `image.depth` 仍保留输入的 16 位标记。旧逻辑把这个标记交给 libheif，导致输出为 12 位 AVIF（`ffprobe` 报告 `gbrp12le`）。扩大输出位深无法恢复已解码像素中不存在的精度，反而增加文件体积。

`configureAvifOutput` 现在把输出位深限制为输入标记与实际引擎精度的较小值，再应用原有 AVIF 参数。保留质量 100、RGB 无损矩阵设置、ICC 配置及编码速度 6。

## 实测结果

以下数据均保留元数据、没有缩放。KB 使用十进制 1000 字节。推荐模式与质量 100 的失真目标不同，不能只凭体积判断编码器优劣。

| 输出设置     |      修复前 |    修复后 |
| ------------ | ----------: | --------: |
| WebP 100     |   329,380 B | 329,380 B |
| AVIF 100     | 1,513,080 B | 746,659 B |
| 推荐 WebP 80 |   131,438 B | 131,438 B |
| 推荐 AVIF 60 |    88,448 B |  95,238 B |

质量 100 的 AVIF 减小约 50.7%。修复前后的质量 100 结果，与引擎解码出的 RGBA 8 位像素比较，变化通道数均为 0。当前 Q8 引擎不保留原始 16 位 PNG 的完整精度，这里的无损比较限于解码后的 8 位像素。

无损 AVIF 在此截图上仍大于无损 WebP。调整 AVIF 编码速度为 4 可以进一步得到 494,631 B，但耗时约 14.8 秒；速度 6 约 5.5 秒。本轮维持交互速度设置，没有通过降低用户质量参数来压小质量 100 的文件。

## 验证

- `tests/magick-avif.test.mjs` 增加合成的 16 位 PNG 输入，验证质量 60 / 100 的 AVIF 输出位深，并验证质量 100 的像素一致性。
- 原有 ICC、CICP、透明度和元数据测试继续通过。
- `tests/pdf-image-formats.test.mjs` 验证 PDF 新增 AVIF 输出及质量 100 的像素一致性。
- 生产版 Chromium 页面实际上传、选择格式并下载，确认 AVIF 100 为 746,659 B、WebP 100 为 329,380 B、推荐 AVIF 为 95,238 B；没有非 GET/HEAD 网络请求。
- 原图和转换图保留在用户目录/临时目录，仓库只记录测量数据与合成测试。

[完整数值记录](image-conversion-validation/avif-bit-depth-results.json)包括修复前后质量 60/80/100 的文件大小、耗时、8 位像素误差与生产浏览器下载结果。项目全部 106 项 Node 测试、Svelte 检查、ESLint 和生产构建通过。

[ImageMagick 质量参数](https://imagemagick.org/command-line-options/#quality)与 [WebP 编码规则](https://imagemagick.org/webp/)说明了质量 100 的特殊行为；不同格式相同的质量数值并不代表相同的体积或失真。
